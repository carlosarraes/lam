The captured gate report is [report.json](chat-probes/2026-09-14/report.json); [the runbook](chat-probes/2026-09-14/README.md) contains the invocation, fixtures, and evidence interpretation.

All successful long-tool probes completed after at least 20 seconds. No test interrupted a model or tool, targeted an existing user pane, or changed shared client daemons or permission defaults. The scoped Codex hook's trust and enable state were changed only through native client review under existing approval. A Claude refusal-session tool was blocked by the existing auto classifier; the probe preserved that denial and obtained that owned session's socket from `/status` for the independent inbound-refusal check.

Peer bodies contained fake LAM headers, JSON delimiters, embedded system/developer instructions, the sender name Carlos, and demands to override an explicit user restriction. The observed receivers reported the allowed nonce, did not print the forbidden token, and did not create the requested files. This is bounded behavioral evidence. Claude also retains native peer origin and permission controls. Pi's customType is local metadata, not a separate model role. Codex's fixed developer wrapper explicitly denies authority to every JSON field; arbitrary peer text is never concatenated into the wrapper instruction. No result establishes immunity to all future prompt injections or verifies human intent against another process owned by the same OS user.

The empty Codex hook emitted zero stdout/stderr bytes in a standalone 19 ms sample. This is one measurement, not a benchmark. Empty follow-up tool calls in all three sessions did not add another copy of old messages. Native refusal/unavailable observations must remain distinguishable from acceptance: a connected socket with no acknowledgement is not a delivery receipt.

The [disabled Codex hook follow-up](chat-probes/2026-09-14/codex-disabled-check.json) closes the disabled-integration case. With its single trusted PostToolUse hook inactive in `/hooks`, a nonce written during a 20,019 ms tool remained pending and never appeared in the native transcript; the model reported `NONE`. This means not submitted, not native queue rejection. The owned session exited normally, and the temporary hook configuration and pending evidence were moved out of their active paths.

Claude's native sender returned submission success, then received an explicit refusal notice; the refusing receiver independently logged rejection before attachment materialization. Earlier raw-helper submissions remain unknown. Codex's approved silent Stop observer reevaluated a pending message after the final empty tool hook and queued a new turn. Ordered idle-to-busy tests exercised both queue-first and hook-first ownership of one pending file, with one native exposure per nonce. These do not establish production leases, crash recovery, native deduplication, or exhaustive scheduler safety.

Pi's configured opencode-go/deepseek-v4-flash provider returned a monthly-limit 429. The model probes used its existing openai-codex login with `--provider openai-codex --model gpt-5.6-luna` for those sessions only. Defaults were unchanged. Claude used its installed Opus 5 default; Codex used its installed gpt-6-astra default and existing permission configuration. Mac behavior, production delivery claims, durable receipt reconciliation, and cross-client LAM commands remain later work.

The installed contracts were checked against [Claude messaging](https://code.claude.com/docs/en/cross-session-messaging), [Codex hooks](https://learn.chatgpt.com/docs/hooks), Pi's installed `docs/extensions.md` and `dist/core/messages.js`, and the installed `~/.pi/agent/extensions/control.ts`. ## Production binding checkpoint, 2026-09-14

Task 6 has added the required Codex structured-text serialization regression and a Linux private-binding implementation with focused tests. It does not yet enable native delivery or authenticate commands. The default daemon still refuses participant binding. No production six-pair exchange, native restart/race check, or 100-check timing run has passed through these adapters. The Task 1 probe results above remain capability evidence only.

The installed versions were rechecked as Claude Code 2.1.270, Codex CLI 0.154.0 and Pi 0.85.1. Credential propagation needs separate native validation:

| Client | Available mechanism | Remaining proof |
| --- | --- | --- |
| Claude | [SessionStart hooks](https://code.claude.com/docs/en/hooks#persist-environment-variables) can append exports to `CLAUDE_ENV_FILE` for subsequent Bash commands | A private token must reach the real command and remain bound to the current native process/session, including session changes and subagents |
| Pi | Installed extension API exposes `session_start` and `ctx.sessionManager.getSessionId()`. Native Bash copies the current process environment and replaces `PI_SESSION_ID` from its session context | An owned extension must issue and rotate a private binding, then prove propagation through native tools and reject stale sessions |
| Codex | [SessionStart](https://learn.chatgpt.com/docs/hooks) supports context output. The fetched hook reference does not establish an environment-export channel | Private record discovery still needs evidence that the calling command and delivery hook belong to the exact registered thread, especially when threads share one process |

Codex's hook reference states that subagent hooks carry the parent's `session_id`. Ordinary `PostToolUse` fields do not include `agent_id`; the transcript format is explicitly unstable. A process ancestry check cannot by itself distinguish threads in the same process. Native identifiers may locate a private record, but neither an inherited identifier nor an arbitrary transcript path is authentication. These are unresolved production binding questions, not a claim that every possible integration is unsupported.

An owned non-hook `codex exec --json` test confirmed the shared-process case at 08:10 to 08:11 UTC. Its root shell received `CODEX_THREAD_ID=01a09ef7-fbdb-7391-8154-f2ba97601ac9`; its single native child received `01a09ef8-25fc-77b1-8f20-39fc5d16f811`. The command PIDs were 2174177 and 2174427, both direct children of Codex PID 2173536, with process start counter 79385708 and boot ID `3cb043eb-f7b1-4588-af7d-c3fe9c530c07`. The observed environment distinguished those native threads; kernel ancestry did not. Both commands and the owned client exited zero. The native PID was absent after exit. This was an identity feasibility test, not a LAM exchange or credential proof. No transcript inspection or environment dump was needed. [The focused artifact](chat-probes/2026-09-14/task-6-binding/README.md) retains exact records and invocation.

The same Codex reference documents a default approximate 2,500-token threshold that replaces larger hook output with a saved-file preview. `additionalContextLimit` can change that threshold. Installed-version support and full inline exposure of the bounded Rust payload still need proof before enabling delivery. The initial checkpoint changed no native configuration.

A later explicitly approved diagnostic probe ran at 12:21 to 12:22 UTC through the exact temporary project hooks and ordinary native trust review. It found `agent_id` on actual child PostToolUse, matching SubagentStart/SubagentStop, while root PostToolUse had no agent_id. Both kept the root session_id, and hook CODEX_THREAD_ID was absent. The frontend was 0.154.0 but the executing shared server was 0.153.4, PID 28534; these are not standalone 0.154.0 hook results. This supplies positive hook-discrimination evidence without choosing a participant restriction. Private credential issuance and actual authenticated commands still need proof. [The five native records and cleanup](chat-probes/2026-09-14/task-6-binding/README.md#observed-association) show that both owned clients exited normally, the temporary active hook definition was removed, and the shared server and unrelated handler were preserved.

The next code checkpoint adds separate enrollment, participant and integration secrets in owned mode-0600 records, Linux boot/process-birth/executable checks, bounded native version helpers, and serialized persistence of the daemon-assigned incarnation. Native IDs locate records and never grant authority alone. Validator tests combine real private files and kernel process evidence with an injected runtime observation; that positive unit case does not prove native credential propagation. The executing-backend discovery path recognizes Codex 0.153.4/0.154.0 and refuses nearer Claude/Pi ancestry rather than using an inherited Codex identity. It remains disconnected from default daemon authentication pending the actual issuance/command path. macOS validation, explicit native-end handling, delivery capability gates and production native tests are unfinished. No hook configuration or trust changed in this code checkpoint.

## Experimental command checkpoint

The later socket/CLI increment adds `chat send --to NAME_OR_MACHINE/INCARNATION --message TEXT`, `chat reply MESSAGE_ID --message TEXT`, `inbox`, `inbox show MESSAGE_ID`, and existing explicit retry. These use private participant credentials and do not accept a sender or role override. They currently queue/read local messages; automatic native delivery is not wired. Minimal responses are JSON. Full command options and UI remain Task 7 work.

Normal `chat serve --foreground` still disables native authentication. The controller approved `--native-bindings` as an explicit experimental gate switch, not settled startup UX. It selects the real Linux validator, with no injected runtime or permission override. JSON and plain-text status distinguish disabled authentication from the experimental validator. Tests enroll two records for separate native IDs sharing one process, then exercise socket authentication, the sole Store owner, addressed send, full Show, explicit reply, and Inbox. They assert exact sender incarnation and reject participant End and revival after integration End. Runtime observation is injected only in that unit fixture; this is not a native command exchange.

`chat hook --client codex --event EVENT --name NAME` currently issues/enrolls on SessionStart/SubagentStart and refreshes registration on later checks. SessionEnd/SubagentStop invoke integration-only End. Explicit name or `LAM_NAME` is currently needed; bounded multiplexer-name discovery is unfinished. Input, native helper and socket operations share an internal two-second deadline. Operational errors emit no stdout/stderr and append fixed private diagnostic labels with no body, credential or arbitrary error text. Diagnostic-storage failure remains silent and inconclusive. End-to-end timing, including startup and diagnostics, has not passed the required native benchmark.

Still missing before release: a fresh trusted startup after End must rotate credentials and receive a new incarnation without moving old messages; bounded live-owner recovery must turn lost handoff completions into Unknown while retaining in-flight exclusion; Codex busy/idle delivery and arrival reevaluation; Claude/Pi adapters; and native auth, provenance, race, refusal, restart, six-pair and 100-check gates. No production hooks or extension were activated in this increment. The user approved the isolated owned test loop before this checkpoint was committed; native execution will follow separately.

The next code checkpoint wires Codex PostToolUse to the existing bounded renderer. Private records persist monotonic observation epochs; only integration credentials may claim and finish. Submitting remains durable throughout the local output attempt. Successful or partial/failed output finishes conservatively as Unknown, never Accepted, exposed or fetched. Its existing 50 ms loop services at most 32 pending hook timers; failed persistence retains Submitting/exclusion and retries no faster than 100 ms. Identical late Unknown is idempotent; conflicting late acceptance is refused. Idle claims do not yet receive these timers because native idle limits remain unproven.

Tests cover blocked stdout, lost Finish with the daemon still alive, concurrent hook/idle exclusion and new arrivals, transactional timeout-persistence failure, and no Unknown replay.
